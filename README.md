# Siberia-hackathon

# AI-ассистент университета

Текстовый ассистент, который отвечает на вопросы о данных университета
на естественном языке: генерирует SQL-запрос, проверяет его на
безопасность и возвращает ответ вместе с таблицей.

## Требования

- Docker + Docker Compose (`docker compose version`)
- Доступ к PostgreSQL с данными университета
- API-ключ Yandex GPT (Foundation Models)

## Быстрый старт

1. Склонировать репозиторий и перейти в папку проекта:

   ```bash
   git clone <ссылка-на-репозиторий>
   cd Hackathon
   ```

2. Создать файл `.env` в корне проекта на основе `.env.example`:

   ```bash
   cp .env.example .env
   ```

   Заполнить переменные:

   ```env
   DATABASE_URL=
   DB_HOST=
   DB_PORT=
   DB_NAME=
   DB_USER=
   DB_PASSWORD=

   API_KEY=
   FOLDER_ID=
   MODEL_NAME=
   API_URL=
   ```

   - `DB_*` — параметры подключения к PostgreSQL
   - `API_KEY`, `FOLDER_ID`, `MODEL_NAME`, `API_URL` — доступ к Yandex GPT

3. Собрать и запустить контейнеры:

   ```bash
   docker compose up --build
   ```

   Или в фоновом режиме:

   ```bash
   docker compose up --build -d
   ```

4. Открыть в браузере:

   ```
   http://localhost
   ```

## Проверка, что всё поднялось

```bash
curl http://localhost:8000/health
```

Должно вернуть:

```json
{"status": "ok", "db": "ok", "uptime_s": 18}
```

`"db": "down"` означает, что сервис жив, а база недоступна — раньше в обоих
случаях отвечалось одинаковое «ok», и индикатор в интерфейсе показывал «на
связи», пока любой вопрос падал.

## Встраиваемый виджет

Публичный ассистент приёмной комиссии, который ставится на любую страницу
одной строкой:

```html
<script src="http://localhost:8080/widget.js" defer></script>
```

Необязательные настройки — атрибутами тега:

```html
<script src="http://localhost:8080/widget.js"
        data-api="http://localhost:8000"
        data-title="Спросить про поступление"
        data-position="right"
        defer></script>
```

Пример встраивания на страницу с чужой вёрсткой: <http://localhost:8080/demo.html>.

**Без входа.** Посетителю сайта незачем заводить логин, чтобы спросить, что
сдавать на прикладную информатику. Виджет берёт токен у `POST /auth/guest` —
без пароля, роль `guest`.

**Граница роли `guest` проведена по одному признаку: видно ли из объекта
конкретного человека.**

Доступно (24 объекта из 57):

- официальный справочник приёма целиком — направления, испытания, места,
  стоимость, сроки, документы, льготы, общежития, контакты, FAQ;
- **расписание занятий** через `public_schedule` (миграция 018) — вузы
  публикуют его открыто, и это самый частый вопрос на сайте;
- справочная обвязка: `pair_times` (звонки), `academic_terms` (даты
  семестров), `rooms` и `campus_buildings` (аудитории и корпуса).

Закрыто:

- **ФИО преподавателей.** `schedule_calendar` гостю недоступен, а в
  `public_schedule` колонки `teacher_name` просто **нет**: запрос
  `SELECT teacher_name FROM public_schedule` не отклоняется проверкой — он
  падает в СУБД, потому что выбирать нечего. Одно дело опубликованное
  расписание занятий, другое — возможность у анонимного посетителя спросить,
  где конкретный преподаватель в четверг в 14:00;
- весь учебный контур: студенты, оценки, задолженности, нагрузка, рейтинги,
  статистика приёма.

Проверяется двумя тестами: `test_guest_sees_only_the_public_admission_reference`
(набор объектов) и `test_public_schedule_carries_no_person` (в представлении
физически нет полей о людях — сломается раньше, чем виджет попадёт на сайт).

Утечка гостевого токена поэтому ничего не даёт: доступно ровно столько,
сколько вуз публикует на сайте.

**Ограничение частоты обязательно.** Токен выдаётся без пароля, а каждый
вопрос — это обращение к платной модели. Считаются по адресу и выдача
токенов, и сами вопросы: 30 обращений за 10 минут, дальше `429` с
`Retry-After` (`throttle.GUEST_MAX`).

**Почему iframe, а не разметка на странице.** Виджет встраивается на чужой
сайт, где уже есть свой CSS и свои `z-index`. Вставленная в документ разметка
неизбежно с ними столкнётся — либо сайт перекрасит виджет, либо виджет
протечёт в сайт. Внутри `iframe` стили изолированы браузером. На странице
хозяина загрузчик создаёт ровно два элемента: кнопку и рамку, глобальных имён
не заводит.

**SQL виден по кнопке.** Под каждым ответом — свёрнутый блок «Показать
SQL-запрос». Посетителю он не нужен, ему нужен ответ; но возможность
посмотреть — это то, чем ассистент над базой отличается от генератора
правдоподобного текста: ответ можно проверить, а не поверить. Показывается и
у отказов — там видно, **что именно** было отклонено.

Отказы для гостя формулируются иначе, чем для сотрудников: посетителю сайта
нечего делать с фразой «доступ выдаёт администратор системы», он прав не
просил (`security.explain_rejection(error, role)`).

## Светлая и тёмная тема

Переключатель в шапке, выбор запоминается в `localStorage`. Начальное
значение — системное (`prefers-color-scheme`), но выбор пользователя его
побеждает.

Вся иерархия интерфейса построена на прозрачностях **одного** цвета поверх
**одного** фона (`--paper-06` … `--paper-70` поверх `--color-asphalt`),
поэтому светлая тема — не второй набор правил, а переопределение тех же
токенов: асфальт и бумага меняются местами. Ни одно правило вёрстки про тему
не знает.

Тема ставится встроенным скриптом в `<head>` **до** отрисовки — иначе при
выбранной светлой странице успевает мигнуть тёмной.

## Эндпоинты

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| GET  | `/health` | без авторизации | живость сервиса **и связь с БД**: `{"status":"ok","db":"ok","uptime_s":18}`. Проверка идёт одной попыткой с коротким таймаутом и кэшируется на 15 с — фронтенд опрашивает эндпоинт каждые 25 секунд |
| POST | `/auth/login` | без авторизации | выдаёт JWT на 8 часов. После 5 неудач подряд на один логин — `429` с `Retry-After` |
| POST | `/auth/guest` | без авторизации | токен роли `guest` для встраиваемого виджета — без пароля и без учётной записи. Ограничен по адресу |
| GET  | `/auth/me` | любая роль | состав проверенного токена. Нужен фронтенду, чтобы не верить роли из localStorage |
| POST | `/chat` | любая роль | вопрос → SQL → проверка → ответ. Возвращает `answer`, `sql`, а также `columns` и `rows` — сами строки из БД |
| GET  | `/meta/data-status` | администрация | сколько данных официальных, сколько демонстрационных |
| GET  | `/meta/stats` | администрация | сводка по `audit_log`: исходы, медиана и p95 времени ответа, топ причин отказа |

`/chat` отдаёт строки отдельными полями `columns`/`rows`, а не только прозой.
Раньше их не было, и фронтенд пытался выпарсить таблицу обратно из текста
ответа — то есть таблица, выгрузка CSV и предупреждение о достигнутом LIMIT
показывались только если модель случайно оформляла ответ разметкой.

## База данных: миграции и данные

Схема `assistant` расширяется только добавлением. Существующие таблицы и
записи не удаляются и не пересоздаются — у каждой записи появилось
происхождение (`data_status`, `source_url`, `checked_at`), по которому бот
отличает официальные сведения ИГУ от демонстрационных данных стенда.

`psql` на стенде нет, поэтому миграции применяет свой раннер на `psycopg`.
Все скрипты по умолчанию работают в режиме просмотра: запись включается
флагом `--apply`.

```bash
# 0. Снимок базы ПЕРЕД любыми изменениями (в backend/backups/, в git не идёт)
python3 backend/scripts/backup_db.py

# 1. Миграции (идемпотентны, повторный запуск безопасен, порядок важен)
for f in 002_ege_scores 005_provenance 006_official_reference 007_schedule_time \
         008_admission_views 009_analytics_views 010_lesson_cancellation \
         011_search 012_analytics_search 013_admission_days \
         014_audit_and_privacy 015_groups_catalog 016_summary_views \
         017_entity_level_views 018_public_schedule 019_unit_search; do
  python3 backend/scripts/apply_sql.py backend/sql/$f.sql --apply
done

# 2. Официальные источники ИГУ: снимки -> датасет -> база
python3 backend/scripts/fetch_isu_sources.py
python3 backend/scripts/build_dataset.py
python3 backend/scripts/seed_official_isu.py --apply
python3 backend/scripts/fix_program_profiles.py --apply   # если каталог грузили старым разбором

# 3. Демонстрационные данные там, где официальных нет
python3 backend/scripts/seed_demo_admission.py --apply
python3 backend/scripts/seed_ege_scores.py --apply

# 4. Расписание
python3 backend/scripts/rebalance_teacher_load.py --apply     # повторять до сходимости
python3 backend/scripts/seed_lesson_occurrences.py --apply
python3 backend/scripts/fix_schedule_conflicts.py             # отчёт
python3 backend/scripts/fix_schedule_conflicts.py --move-across-days --apply

# 5. Проверки
python3 backend/tests/test_security_and_auth.py   # БД не нужна
node    backend/tests/test_frontend_render.js     # ни БД, ни сети
python3 backend/tests/test_data_integrity.py      # нужна БД
python3 backend/tests/test_demo_questions.py      # нужна БД
python3 backend/tests/eval_live_questions.py      # нужны БД и Yandex GPT
```

Проверкам нужны зависимости из `backend/requirements.txt`, установленные **на
хосте**: запускаются они из корня репозитория (`import backend.app...`), а внутри
контейнера `/app` — это `./backend`, и такой импорт там не соберётся.

**Перед защитой обязательно прогоните `eval_live_questions.py`.** Остальные
тесты проверяют данные и правила на рукописном SQL, а этот — весь путь
целиком: вопрос → модель → SQL → проверка → база → ответ. Ровно в зазоре
между ними и жили все найденные промахи: «сколько должников на кафедре
Программная инженерия» проходило на рукописном SQL и падало на живом, потому
что человек пишет название в именительном падеже. Прогон занимает около семи
минут и примерно 80 обращений к модели.

Про шаг 4. Разгрузку преподавателей надо делать ПЕРВОЙ: пока у одного
человека 63 занятия в неделю при 42 слотах, бесконфликтного расписания не
существует ни при какой перестановке пар. Скрипт разгрузки за один проход
снимает один курс с каждого перегруженного, поэтому его запускают несколько
раз, пока «Передач курсов» не станет 0.

`fix_schedule_conflicts.py` без флагов переносит занятия только внутри того же
дня недели — так уже разложенные даты остаются верными. С
`--move-across-days` он может менять день и сам пересчитывает даты в
`lesson_occurrences`: лишние проведения не удаляются, а помечаются
отменёнными (`cancelled_at`).

### Подразделение не участвовало в поиске

Вопрос «на физмат» не понимался. Первая догадка — не хватает прав роли
`guest` — оказалась неверной: тот же вопрос под администрацией, у которой
доступны все объекты, тоже возвращал пусто. И не только «физмат», но и полное
«физический факультет».

Причина общая и не про доступ. `edu_programs.search_vector` — генерируемая
колонка из `name`, `profile` и `code`; названия факультета или института в ней
нет. А `programs_admission`, `program_exam_sets` и `passing_scores_view`
отдавали `ep.search_vector` как есть. При этом `unit_name` в них **есть** и
показывается в ответе: увидеть подразделение можно, найти по нему — нельзя.
У Физического факультета семь направлений, поиск по его названию возвращал
ноль.

Миграция 019 добавляет к вектору направления вектор его подразделения, плюс
словарь разговорных сокращений `unit_search_aliases`: «физмат», «юрфак»,
«истфак», «имит», «филфак», «педфак», «химфак» и так далее. Абитуриенты пишут
именно так, а ни в одном официальном документе таких слов нет и быть не может.

Про природу словаря: это **не** сведения об университете и не официальные
названия, поэтому колонки `data_status` у него нет — помечать происхождение
нечему. Он участвует только в сопоставлении и никогда не попадает в ответ: там
всегда официальное название из `university_units`.

«Физмат» намеренно ведёт на **два** подразделения — физический факультет и
институт математики. Слово разговорное и неоднозначное; показать оба варианта
честнее, чем молча выбрать один и выдать догадку за факт.

Отдельно из `programs_admission` убраны `unit_short_name` и `duration_years`:
обе пусты у **всех** строк (0 из 15 и 0 из 113). Колонка, способная вернуть
только NULL, ответа не даёт, но приглашает модель её выбрать.

### Поиск с учётом падежей

У `programs_admission`, `program_exam_sets` и `passing_scores_view` есть
колонка `search_vector`. Запрос строится так:

```sql
SELECT program_name, tuition_rub FROM programs_admission
WHERE search_vector @@ plainto_tsquery('russian', 'программной инженерии');
```

Словарь `russian` приводит словоформы к основе, поэтому `ILIKE` с угаданным
корнем больше не нужен. Подбор направления по набору ЕГЭ идёт по коротким
именам предметов: `required_short <@ ARRAY['русский','математика','информатика']`.

### Происхождение данных

`data_status` принимает четыре значения: `official` (подтверждено официальным
источником ИГУ, ссылка обязательна), `historical` (официальные данные прошлых
лет), `demo` (демонстрационные данные стенда), `unverified` (подтвердить не
удалось, значение `NULL`).

Колонка **служебная**: она нужна загрузчикам данных, отчётам и проверкам
целостности. В ответ пользователю она не попадает — промпт запрещает и
включать её в `SELECT`, и упоминать происхождение данных в ответе. Ссылки на
сайт в ответах тоже не выводятся: ответ должен быть самодостаточным.

Сводку по статусам отдаёт `GET /meta/data-status` (под авторизацией) или
представление `assistant.data_status_summary`.

Минимальный и проходной баллы лежат в разных таблицах и не смешиваются:
минимальный — порог допуска к конкурсу, проходной — балл последнего
зачисленного в конкретном году, форме и основе обучения.

### Демо-контур и официальный каталог

В базе два непересекающихся слоя данных, и модель видит только один из них.

**Официальный каталог ИГУ** — `university_units` (15 подразделений),
`edu_programs` (113 направлений) и приёмная кампания вокруг них. Именно
отсюда берутся ответы о структуре университета и о поступлении.

**Демонстрационный контур** — `faculties` (5 выдуманных факультетов),
`programs` (13 направлений) и `departments`. На них завязаны 4981 студент,
139 групп, расписание и оценки, поэтому таблицы работают и остаются в базе,
**но в whitelist модели их нет**. Причина: пока обе структуры видны, на
вопрос «сколько факультетов в ИГУ» модель отвечала «пять» вместо
пятнадцати — выбор между источниками был лотереей.

Названия факультетов, направлений и кафедр доступны текстом в аналитических
представлениях (`faculty_name`, `program_name`, `department_name`), так что
ничего не теряется.

### Висячие внешние ключи: почему модель соединяла несоединимое

У сокрытия таблиц была цена, и она вылезла на вопросе «какие группы учатся на
направлении информационная безопасность». Модель выдала:

```sql
SELECT DISTINCT g.name FROM groups g
JOIN edu_programs ep ON g.program_id = ep.id
WHERE ep.name ILIKE '%информационная безопасность%'
```

Ноль строк — и не могло быть иначе: `groups.program_id` ведёт в `programs`
(демо-контур, 13 направлений), а `edu_programs` — официальный каталог на 113.
`program_id` там не больше 13, а нужные строки каталога имеют id 108 и 109.
Ответ в базе при этом был: по правильной связи это направление изучают 17 групп.

Виновата не модель. `programs` от неё скрыта, поэтому связь
`groups.program_id -> programs.id` выпадала из блока связей, и в промпте
оставалась колонка `program_id` **без единого объявленного соединения** — рядом
с подходящим по названию `edu_programs`. Соединить их было единственным
доступным ходом.

Теперь `ai_agent.get_db_schema()` вычищает такие колонки из схемы: если внешний
ключ ведёт в невидимый роли объект, колонка модели не показывается вовсе.
Соединить по ней невозможно. Список берётся из живых constraint'ов, а не из
перечня в коде — сейчас под фильтр попадают `groups.program_id`,
`curriculum.program_id`, `admission_campaigns.program_id`,
`teachers.department_id`, `subjects.department_id`, а у роли `student`
дополнительно `schedule.curriculum_id`.

У представлений внешних ключей не бывает, поэтому те же две ссылки
(`ege_scores_summary.faculty_id`, `students_summary.faculty_id`) сначала были
перечислены в коде списком. Список описывал дефект, но не устранял его, поэтому
устранён он там, где возник: миграция 016 отдаёт `faculty_name` вместо
`faculty_id`. Заодно появилась возможность, которой не было, — «средний балл ЕГЭ
по факультетам» раньше нельзя было даже сформулировать: группировать было не по
чему, кроме безымянного числа.

Вопрос «какие группы на направлении X» отвечает `groups_catalog` (миграция 015):
названия группы, направления и факультета лежат там текстом, соединять нечего.

### Строка представления — не всегда то, чем кажется

На вопрос «сколько должников учится на кафедре» ассистент ответил: **«на
кафедрах в сумме обучается 10760 студентов с долгами»** — при 4981 студенте в
университете. Ответ невозможен арифметически.

Модель не ошиблась: её поставили в положение, где ошибиться было проще.
`academic_debts` группируется по `s.id` **и** `d.name`, то есть строка там —
пара «студент × кафедра»: 16 364 строки на 4 566 студентов. Один вопрос про
кафедру программной инженерии давал три разных числа:

| запрос | результат | что это на самом деле |
|---|---|---|
| `SUM(debts_count)` | 488 | задолженности, а не люди |
| `COUNT(*) WHERE debts_count > 0` | 400 | пары «студент × кафедра» |
| `department_debts.debtors_count` | 349 | **люди** |

Второй вариант был записан как эталонный SQL в `test_demo_questions.py` —
тест проверял непустоту выборки и потому закреплял неверный запрос.

Та же ловушка была в `subject_performance`: «Базы данных» читаются на двух
направлениях, поэтому строк две, и ассистент честно отвечал «по одним данным
88%, по другим — 86,8%». Однозначного ответа в этом представлении не
существовало.

Лечится не правилом в промпте, а данными (миграция 017):

| представление | строка = |
|---|---|
| `student_debts` | один студент — для «сколько должников», «кто не сдал ни одного экзамена» |
| `department_debts` | одна кафедра — `debtors_count` (люди) и `debts_total` (задолженности) разведены явно |
| `subject_summary` | одна дисциплина — доля сдавших считается от общих итогов, а не усредняется по строкам |

Плюс механизм, чтобы это не повторилось на следующей вьюхе: **разрез каждого
объекта записан в `COMMENT ON VIEW` и попадает в промпт** рядом с колонками
(`ai_agent.fetch_object_comments`). По имени и списку колонок отличить «строка
= студент» от «строка = студент × кафедра» невозможно — теперь и не нужно,
подпись видна там же:

```
- academic_debts: last_name (text), ..., debts_count (bigint)
    Строка = пара «студент × кафедра»: студент встречается столько раз,
    сколько кафедр ведёт его предметы. Для подсчёта ЛЮДЕЙ берите student_debts.
```

Заводите новое представление — напишите ему `COMMENT`, и модель узнает о его
разрезе сама. Списка в коде для этого нет и не нужно.

### Разбор приложения к Правилам приёма

Профиль направления доставался из заголовка жадным `re.search(r"\((.*)\)(.*)$")`
— от **первой** открывающей скобки до **последней** закрывающей. На заголовке

```
Педагогическое образование (с двумя профилями подготовки) (Математика -Информатика)
```

получалось название «Педагогическое образование» и профиль
«с двумя профилями подготовки) (Математика -Информатика»: посторонняя скобка
посреди строки, уточнение из официального названия потеряно.

Поражено это было у **26 записей каталога из 113**, а заметно становилось лишь
у пяти — у остальных скобки случайно сходились по количеству, и проверка
баланса их не ловила. Хуже всего пострадали те, где скобка стоит внутри
названия: направление 44.03.03 называлось в базе просто **«Специальное»**
вместо «Специальное (дефектологическое) образование».

Разбор переписан (`build_dataset.split_title_and_profile`): скобочные группы
разбираются по уровням вложенности, профиль — последняя группа верхнего уровня,
всё до неё остаётся в названии. Недостающие закрывающие скобки (их теряет
извлечение текста из PDF) дописываются перед разбором.

Уже загруженные данные чинит `backend/scripts/fix_program_profiles.py`: он
восстанавливает исходный заголовок из сохранённых значений и раскладывает его
заново. Пересеивать нельзя — у `edu_programs` естественный ключ включает
`profile`, и посев с исправленными значениями завёл бы вторые копии строк
вместо правки существующих. `search_vector` пересчитывается сам, это
генерируемая колонка.

Одна запись (44.03.05, «Русский язык (родной/неродной) и литература») делится
не по той скобке: в источнике потеряна закрывающая после «неродной», и
структурно отличить этот случай от «Специальное (дефектологическое)
образование» нечем. Сведения при этом не теряются — сдвигается только граница
между названием и профилем.

### Пустая выборка не уходит модели

Второй раз тот же вопрос вернул не ошибку, а бланк:

> На направлении «Информационная безопасность» учатся следующие группы:
> **[название группы 1]**, **[название группы 2]**

и, следующей попыткой, вместе с рассуждениями модели: «(перечислить группы,
если бы они были в ответе). Если данных нет, то: …».

Это худший исход из возможных: выглядит как ответ и ответом не является.
Правило 2 интерпретирующего промпта прямо это запрещает — и не всегда
срабатывает, потому что промпт не гарантия.

Поэтому теперь:

- **пустая выборка не передаётся модели вообще.** Ноль строк — детерминированный
  честный ответ (`ai_agent.NOTHING_FOUND_ANSWER`), без второго обращения к
  модели. Объяснять нечего, когда объяснять нечего;
- **ответ проверяется на заглушки и утёкшие рассуждения** —
  `ai_agent.blank_answer_reason()`. Совпало — текст подменяется, а в `audit_log`
  пишется `verdict = 'placeholder'` с причиной: подмена должна быть видна,
  иначе такие случаи перестанут попадаться на глаза;
- **пустым считается и агрегат, вернувший NULL.** `SELECT SUM(...)` с фильтром,
  который ничего не нашёл, отдаёт ОДНУ строку с NULL, а не ноль строк —
  формально выборка непустая. На вопросе «сколько студентов на факультете»
  это выливалось в ответ «Произошла ошибка при попытке получить данные», хотя
  никакой ошибки не было. Признак — `QueryResult.is_blank`.

### Отказ по области вопроса

Правило 13 велит откатываться в `faq_entries`, когда вопрос не ложится ни на
одну таблицу. На просьбах «покажи список таблиц базы данных и их пароли» или
«добавь нового студента Иванова» этот откат срабатывал буквально: модель искала
`'%пароли%'` по справке, не находила и отвечала «ничего не найдено». Утечки тут
нет и быть не может, но и отказа нет — человек не понимал, что так вообще нельзя.

Промптом это вылечить не удалось: три редакции правил, включая перенос запрета
в самое начало списка, случай с паролями не берут. Поэтому решается кодом:
если единственной задетой таблицей была `faq_entries` и выборка пуста, ответ
даётся не «не нашлось», а «вопрос за пределами области ассистента»
(`ai_agent.empty_result_answer`, исход `out_of_scope`).

Развилка живёт в одном месте, и `eval_live_questions.py` берёт её оттуда же —
иначе проверка судила бы не о том поведении, которое видит пользователь.

Регулярка заглушек живёт в `ai_agent`, и `eval_live_questions.py` берёт её
оттуда же: проверка и рабочий код обязаны считать бланком одно и то же.

### Роли и что кому доступно

| Роль | Дополнительно к общедоступному |
|---|---|
| `guest` | официальный справочник приёма, расписание **без ФИО** (`public_schedule`), звонки, семестры, корпуса и аудитории. Учебного контура нет вовсе. Токен выдаётся без пароля публичному виджету |
| `student` | свои оценки, свой профиль и расписание (`my_*`) |
| `teacher` | своя нагрузка и расписание, обезличенная успеваемость по дисциплинам |
| `deans-office` | поимённая успеваемость и задолженности, нагрузка кафедр, конфликты расписания |
| `administration` | всё выше плюс статистика приёма и баллы ЕГЭ |

Общедоступно любой роли: официальный справочник ИГУ, расписание, аудитории,
учебные планы, преподаватели. Паспорта, телефоны, почты и даты рождения
закрыты для **всех** ролей без исключения — они в `security.FORBIDDEN_COLUMNS`.

Роль берётся из подписанного JWT, а не из тела запроса: подменить её на
клиенте нельзя. При отказе пользователь видит объяснение словами
(`security.explain_rejection`), а точная причина уходит в `audit_log`.

Служебные эндпоинты `/meta/data-status` и `/meta/stats` доступны только
администрации: первый показывает, где в базе стоят демонстрационные значения,
второй — журнал обращений. Это инструменты владельца системы, а не ответ
пользователю.

### Подбор пароля

`/auth/login` считает неудачные попытки по имени пользователя: пять за пять
минут — и дальше `429` с заголовком `Retry-After`, пока окно не истечёт.
Успешный вход счётчик обнуляет. Проверка стоит **до** сверки пароля, чтобы
перебор не тратил ни bcrypt (сотни миллисекунд на попытку), ни соединение с БД.

Счётчик живёт в памяти процесса (`backend/app/throttle.py`) — писать в базу на
каждую неудачную попытку значило бы отдать перебору ещё и запись. При
нескольких репликах ограничение станет «N попыток на реплику»; для стенда это
приемлемо, для реального развёртывания нужен общий Redis.

Ключ — имя пользователя, а не адрес: в docker-раскладке адрес у всех один
(запросы идут через контейнер фронтенда), и блокировка по нему выключила бы
вход сразу всем.

Все три исхода входа (`login_ok`, `login_failed`, `login_throttled`) попадают в
`audit_log`. Паролей там нет и быть не может — в наборе полей
`log_audit_entry` их просто не существует.

### Мониторинг и логирование

Каждое обращение к `/chat` и `/auth/login` пишется дважды: строкой в stderr
(видно в `docker compose logs backend`) и записью в `assistant.audit_log`.
До этого в лог попадали только сбои, поэтому на работающем стенде
`docker compose logs` оставался пустым.

```
[chat] user=student role=student verdict=ok rows=17 total_ms=6212 llm_ms=5980 q='Какие группы...'
[login] user=victim verdict=throttled retry_after=283
```

Исходы в `audit_log`:

| verdict | что означает |
|---|---|
| `ok` | ответ отдан по данным из базы |
| `empty` | выборка пуста — ответили честно, модель к объяснению не привлекали |
| `out_of_scope` | отвечали только поиском по справке и не нашли: вопрос не про наши данные |
| `rejected` | запрос отклонён проверкой безопасности, причина в `reject_reason` |
| `db_error` | СУБД не выполнила запрос даже после самоисправления |
| `placeholder` | модель выдала бланк вместо ответа, текст подменён |
| `no_sql` | модель не вернула SQL |
| `login_ok` / `login_failed` / `login_throttled` | исходы входа |

`db_error` появился не просто так: раньше запрос, упавший в СУБД даже после
повторной попытки, записывался как `ok`. То есть мониторинг показывал успех
там, где пользователь видел ошибку.

Сводку отдаёт `GET /meta/stats` (только администрации): количество по исходам
за всё время и за сутки, медиана и p95 времени ответа, доля времени в модели,
топ причин отказа. Ровно это и стоит показывать на защите вместо слов
«логирование у нас есть».

### Самоисправление запроса

Если СУБД вернула ошибку, `/chat` делает **одну** попытку исправиться: модель
получает свой запрос вместе с текстом ошибки и переписывает его. PostgreSQL
отвечает конкретно — `column "semester" does not exist`, — и этого хватает,
чтобы поправить колонку с первого раза.

Из-за повтора модель вызывается до трёх раз за вопрос, поэтому
`REQUEST_TIMEOUT_MS` во фронтенде — 150 секунд. Меняете `LLM_TIMEOUT_S` или
`LLM_RETRIES` — сверьтесь с ним.

## Пересборка после изменений

Изменения в `backend/` подхватываются автоматически (uvicorn `--reload`
+ смонтированный volume). Изменения в `frontend/` требуют пересборки
образа:

```bash
docker compose build --no-cache frontend
docker compose up -d frontend
```
